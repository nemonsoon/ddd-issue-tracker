# 設計判断とトレードオフ

[← README](../README.md)

なぜこの技術・この構造を選んだのかを確認したいときに読む。採用しなかった候補とその理由も扱う。

## オニオンアーキテクチャ採用

レイヤードアーキテクチャではなくオニオンアーキテクチャを採用。  
レイヤードでは上位層が下位層に直接依存するため、データベースの変更がドメインに波及する。オニオンではDomain層が依存の中心となり、InfraがDomainのインターフェースを実装する（依存性逆転）。テスタビリティとドメインの独立性を確保。

## Anemic Domain Model

Entityにドメインメソッドを持たせず、型定義のみ。  
現在のCRUD中心の実装ではRich Domain Modelの恩恵が薄い。層分離の構造を確立した後、ドメインロジックが増えた段階でメソッドを追加する。

## 層の分離にどこまで投資するか

投資するのは依存の向きと整合性の境界に限る。
層の数、ディレクトリ構成、同心円の図の再現には投資しない。

原典である [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)（2012-08-13）が挙げているのは、フレームワーク非依存・テスト可能・画面非依存・データベース非依存・外部非依存の5点と、「依存の向きは内向きのみ」という1つの規則だけである。
円が4つ描かれているのは図解の都合だと著者自身が明記している。

この線引きは外部の実測データとも整合する。

- [DORA 2025年レポート](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)（2025-09-23）は、結合の緩いアーキテクチャと速いフィードバックを持つチームは生成AIの導入で成果を得るが、結合の強いシステムと遅い工程のチームはほとんど得ないと報告している
- [Balancing AI tensions](https://dora.dev/insights/balancing-ai-tensions/)（2026-03-10）は、強いAPIと明確なワークフローと強いテストが無い組織では、生成AIが技術的負債を加速するとしている

つまり「生成AIが書くから設計の分離は不要になる」という筋は、現時点のデータからは支持されない。

上記の出典と数値は 2026-08-31 に本文を照合済み。

## 採用しなかったもの

立ち上げ時（2026-05）に候補へ挙げたが、意図的に外したもの。

| 候補 | 外した理由 |
| --- | --- |
| fp-ts | 関数型のイディオムを同時に導入すると、層分離に由来する複雑さと切り分けられなくなる |
| TypeORM | Prisma のほうが型安全とマイグレーションの扱いで優る |
| Inversify | 下記「DIコンテナ不使用」を参照 |
| CQRS / Event Sourcing | 提唱側の [Martin Fowler](https://martinfowler.com/bliki/CQRS.html)（2011-07-14）自身が「大半のケースはうまくいっていない」と記し、適用先を境界づけられたコンテキストなど一部に限るよう処方している。このリポジトリの規模では利点が立たない |

## DIコンテナ不使用

InversifyなどのDIコンテナを使わず、`apps/api/src/container.ts` と `apps/api/src/main.ts` で手動配線する。  
依存グラフが小規模（Repository 1つ、UseCase 5つ）であり、コンテナのデコレータ・リフレクション等の暗黙的挙動が利点を上回る。規模拡大時に導入を検討。

## statusをString型で保持

データベースのスキーマ上はenum制約を設けず、アプリケーション層のunion type (`"open" | "closed"`) で型安全性を確保。  
PostgreSQL enumは`ALTER TYPE`によるマイグレーションが煩雑。アプリケーションコードで制御する方がスキーマ変更に柔軟。

## テスト戦略: Fake > Mock

モックライブラリを使わず、手書きのFake Repositoryでテスト。  
Fakeはインターフェースの完全な実装であり、テスト対象の振る舞いをより正確に検証できる。モックは実装詳細への結合が起きやすい。

## エラーの層配置と「見つからない」の扱い

エラーを2層に分けて配置する。

- **ドメインエラー**（`apps/api/src/domain/issue/errors.ts`）: ドメインのルール違反。例: `InvalidIssueTitleError`（タイトルが空）。ドメイン自身の不変条件を破ったときに発生する。
- **アプリケーションエラー**（`apps/api/src/usecase/issue/errors.ts`）: ユースケース実行上の失敗。例: `IssueNotFoundError`（指定IDのIssueが存在しない）。

`IssueNotFoundError` をドメインではなく **UseCase 側**に置く理由は依存方向にある。「見つからない」を UseCase の関心とすれば、Repository（内側）は UseCase（外側）のエラーを import せずに済み、オニオンの依存方向（外→内）が自然に保たれる。逆に Repository がこのエラーを throw する設計だと、内側が外側に依存することになり破綻する。

したがって **Repository は「見つからない」を throw しない**。`findById` は `Issue | null` を返し、UseCase が null を検知して `IssueNotFoundError` を throw する。`update` / `delete` も同様に、UseCase が先に `findById` で存在確認し、無ければ throw する（Repository は純粋な永続化に徹する）。

「結果0件」と「見つからない」は区別する。一覧取得（`findAll`）の0件は正常系（空配列）、ID指定の取得・更新・削除で対象が無いのはアプリケーションエラー。

## バックエンドと画面を apps 配下に並べる

リポジトリのルートを pnpm のワークスペースとして扱い、バックエンドを `apps/api`、画面を `apps/web` に置く。
ルートの `package.json` はワークスペース全体のスクリプトだけを持ち、どちらのアプリの依存も持たない。

当初は、バックエンドをルートに残したまま画面だけを `apps/web` に足す案を採っていた。
この案では階層が揃わず、ルートの `package.json` がバックエンドの依存とワークスペースの指揮を兼ねる。
`pnpm --filter web` はあるのに `--filter api` は無い、という非対称もここから生まれる。
初めてリポジトリを開いた人に「なぜバックエンドだけルートにいるのか」を説明させる形になるため、揃える側を選んだ。

画面とバックエンドは HTTP だけでつながる。
画面が Domain 層や UseCase 層のコードを直接読み込まないため、画面を足しても依存の向きは外から内のまま保たれる。

## 画面の枠組みに Vite と TanStack Router を選ぶ

画面は Vite で静的なファイルとして書き出し、公開時は Hono が同じサーバーから配る。

TanStack Start と Next.js は採用しなかった。
どちらも画面を配るためのサーバーを自前で持つため、Hono と合わせるとサーバーが2つになる。
この構成では、起動手順が2系統に分かれ、どちらが何を担当するのかを読む側に説明させることになる。

サーバー側レンダリングが効くのは、検索エンジンに拾わせたい場合や、初回表示の速さが要る場合である。
このリポジトリは課題一覧の1画面だけなので、どちらも当てはまらない。

Next.js はさらに、HTTP の入り口を自分の中に置く書き方（Route Handlers、Server Actions）を標準としている。
層分離を見せることが目的のリポジトリで、API の置き場所が2か所に見える構成は避けた。

## 入力検証を Zod とドメインで分担する

Presentation 層の Zod が確かめるのは、受け取った値の「形」だけにする。
題名が文字列か、`status` が扱える値かを見る。

題名が空であってはならないという業務規則は、Domain 層の `InvalidIssueTitleError` が持つ。
Zod 側に `min(1)` を重ねると同じ規則が2か所に散り、片方だけ変えたときに食い違う。

Presentation 層は `InvalidIssueTitleError` を捕まえて 400 へ変換する。
規則そのものは内側に1つだけ置き、外側はその結果を HTTP の言葉に翻訳する役割にとどめる。

## 保存形式とドメインの形のずれを Infrastructure で吸収する

データベースの列とドメインの型は一致しない。
`description` 列は NULL を許すが、ドメインの `Issue` は `string` を要求する。
`status` 列はただの文字列だが、ドメインは `"open" | "closed"` の union type を要求する。

このずれは `apps/api/src/infra/issue/prismaIssueRepository.ts` の変換関数だけで吸収する。
`description` の NULL は空文字へ寄せ、`status` は Domain 層の型ガード `isIssueStatus` を通してから返す。

型アサーション（`as`）で押し通さない。
保存されている値が想定外だったときに黙って通ると、誤った値がドメインの内側へ入り込む。
型ガードが通らなければ `UnknownIssueStatusError` を投げて、その場で止める。

## updatedAt を Prisma の @updatedAt に任せない

`updatedAt` の値は UseCase 層が決める。
`UpdateIssueUseCase` が更新時刻を組み立てて Repository へ渡すため、Prisma のスキーマからは `@updatedAt` を外した。

`@updatedAt` を付けたままだと、保存の直前に Prisma が時刻を差し替える余地が残る。
どちらが最終的な値を決めるのかが読んで分からない状態になるため、決定権を UseCase 側の1か所に寄せた。

`@default` は残している。
こちらはデータベース側の定義（DDL）に現れるため、外すとマイグレーションが必要になる。
Repository は保存時に常に値を明示するので、既定値が使われる経路はない。

## 画面の意匠は Mantine の既定をそのまま使う

色、余白、文字サイズ、角丸、文字の太さ、行間は、Mantine 9 の既定をそのまま使う。
独自のテーマファイルは置かない。

このリポジトリの学習の主眼はバックエンドにある。
画面に独自の意匠を持たせると、色と目盛りを決め直す作業が部品を足すたびに発生し、そちらに時間を取られる。
既定に寄せておけば、見た目の判断そのものが不要になる。

配色は既定の色名だけを使い、CSS からは `var(--mantine-color-<名前>-<段階>)` で参照する。
主要な操作に `blue`、完了に `teal`、失敗に `red`、背景と罫線に `gray` を割り当てている。
CSS に個別の色や余白を直接書かない。
同じ色が複数のファイルに散ると、配色を変えるときに取りこぼす。

手書きの部品も置かない。
一覧は `Table`、状態の表示は `Badge`、絞り込みは `SegmentedControl`、完了率の円は `RingProgress`、読み込み中の仮表示は `Skeleton` を使う。

Mantine に対応する目盛りが無い骨格の寸法（上の帯の高さ、右の列の最小幅、外周の余白、列の間隔）だけ、`apps/web/src/styles/tokens.css` にカスタムプロパティとして集めている。
`apps/web/src/styles/global.css` が引き受けるのは、Mantine の baseline がリセットしない見出しとリストの余白だけである。

画面幅の区切りは Mantine の breakpoint と同じ値を使う。
カスタムプロパティはメディアクエリの中で使えないため、この値だけは各 CSS ファイルに直接書き、`tokens.css` の冒頭に一覧を残している。

`.tsx` の中の数値（アイコンの大きさ、線の太さ、表示件数）は `apps/web/src/constants.ts` に集める。

## 課題の詳細は右の列に出し、行の中では開かない

課題を選ぶと、右の列が「今週の注目事項」からその課題の詳細に入れ替わる。
行の下に詳細を差し込むアコーディオンは採らない。

アコーディオンは、一覧の文脈を保ったまま少しだけ覗くための仕掛けである。
説明文と作成日時と識別子を並べる量になると、開いた行が下の行を押し下げ、一覧が視界から消える。
覗く量を超えたものを、覗くための仕掛けで出していたことになる。

選択した課題は URL の検索引数 `selected` に持たせ、読み込みの依存には入れない。
依存に入れると、課題を選ぶたびに一覧の取得が走る。
詳細に出す値は一覧の取得ですでに手元にあるため、`GET /api/issues/:id` は足していない。

絞り込みを変えたときは選択を外す。
選んだ課題が一覧から消えたまま詳細だけが残ると、並びと詳細の対応が崩れるためである。
共有された URL の識別子が一覧に無いときも、同じ規則で選択を外す。
